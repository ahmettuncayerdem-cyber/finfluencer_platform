## 2. Commit Plan

### 2.1 Ordering principle

Commits are ordered by **dependency**, not by chat chronology (the same principle Milestone 2.7A.1 established and you approved). Within Sprint 1/2, a module is committed only after everything it imports already exists in history. Sprint 2.7A's commits follow, each independently buildable against the Sprint 1/2 baseline.

### 2.2 Why files first introduced during Sprint 1/2 include their later Sprint 2.7A.2 fixes, not a separate "fix" commit

`main.py`, `job.py`, `orchestrator.py`, `manuscript_figures.py`, `manuscript_tables.py`, and their tests have **never been committed**. Their on-disk content today already includes both the original Sprint 1/2 implementation and the Sprint 2.7A.2 lint/type fixes (B904, stale `# noqa`, `B905`, `F401`, the `S110` logging fix, two `mypy` stub-precision `type: ignore`s). Git has no prior committed snapshot of these files to diff against, so there is no mechanical way to split "add the file" from "fix it" into two atomic commits — a "fix" commit requires something to fix *against*. Fabricating an artificial two-step history here (commit the unfixed version, then immediately "fix" it) would misrepresent what actually happened, which is exactly the anti-pattern Milestone 2.7A.1 already rejected for the same reason ("reconstructs a logical, dependency-safe git history instead of trying to replay the chronological order of the chat"). **Conclusion: these fixes are folded into each file's one, first-appearance commit — not split further.**

### 2.3 Why `pyproject.toml` and `CONTRIBUTING.md` *are* split, unlike the files above

Both are **tracked** files with a real prior commit in history — `git diff` against that baseline shows two non-adjacent, non-overlapping hunks each (confirmed by inspection: `pyproject.toml`'s dependency addition sits at line ~133, its Ruff/MyPy config addition at line ~310+, separated by ~175 unchanged lines; `CONTRIBUTING.md`'s CI-policy section and its Versioning-and-releases section are separated by the unchanged "Commit discipline" paragraph). Because a real baseline exists, `git add -p` can mechanically stage one hunk without the other. This is a genuine, achievable split, unlike 2.2 — so it is done.

**Commands** (run before Commit 3 and Commit 9 respectively; `git add -p` will prompt per hunk — answer `y` to the hunk described, `n` to the other):

```bash
git add -p pyproject.toml   # Commit 3: accept only the pymannkendall/scikit-posthocs dependency hunk
# ... later, before Commit 9:
git add -p pyproject.toml   # Commit 9: accept the [tool.ruff.lint.per-file-ignores] + [[tool.mypy.overrides]] hunks
git add -p CONTRIBUTING.md  # Commit 9: accept only the "CI quality gate scope" hunk
# ... later, before Commit 13:
git add CONTRIBUTING.md     # remaining hunk ("Versioning and releases") — the whole file's diff is now exhausted, plain `git add` is safe here
```
