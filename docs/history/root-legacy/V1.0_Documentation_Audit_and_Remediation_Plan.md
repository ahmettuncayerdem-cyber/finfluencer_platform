# V1.0 Documentation Audit & Remediation Plan

**Role:** Release Manager, Finfluencer Research Platform
**Scope:** Audit of release-facing documentation ahead of the v1.0.0 tag. R1–R5 of the Repository Hygiene & Release Remediation Plan are marked complete (coverage 75.71%); this audit covers the documentation layer that sits on top of that engineering work.
**Method:** Direct repository inspection (file listing, `git status`, `git tag`, `git log`, `pyproject.toml`, `config/settings.yaml`, full-text search across every `.md` file). No files were modified to produce this report.

---

## 0. A finding that changes the priority of everything else

Before the individual documentation items: `git status` shows the CI workflow (`.github/`) and the CLI entry point (`src/finfluencer/cli.py`) — both marked "completed" in the Repository Hygiene & Release Remediation Plan as R4 and R2 respectively — are **untracked**, not committed to any branch. So is essentially all of the R5 coverage-remediation test suite added this session (`tests/unit/test_utils/test_io.py`, `tests/unit/test_collect/test_quota.py`, `tests/unit/test_providers/test_english.py`, and the extensions to `test_budgets.py`, `test_config.py`, `test_registry.py`, `test_reproducibility.py` all show as modified-but-uncommitted). The repository is also currently on branch `phase2-development`, not `master`, and only 4 commits exist on it (`8a2a015`, `e3121e4`, `356230f`, `91f151e`). `git status --short` reports 176 lines of changed/untracked state, 133 of them untracked files.

**Practical consequence:** if a `v1.0.0` tag were cut right now, it would not actually contain the CI pipeline, the fixed CLI entry point, or the coverage-remediation tests that R1–R5 were just certified against. Every item below assumes this gets resolved first, because no amount of correct documentation fixes a release that doesn't contain the code the documentation describes. This is folded into the "Versioning consistency" item (§11) but is really the root cause behind several others.

## 1. Audit findings by item

### README — **Missing** (in substance)

Two files compete for this role. `README.md` (27 bytes) contains only `# Finfluencer Platform` — a title and nothing else. `README.txt` (1.3 KB) is not a README at all; it's a dated internal patch note ("Finfluencer Research Platform — Windows Test Fix," generated 2026-07-11) documenting a POSIX/Windows test compatibility fix. Since `pyproject.toml` declares `readme = "README.md"`, that near-empty file is what PyPI/GitHub would render. There is no project description, no install steps, no usage example, no license/citation pointer — nothing a new visitor needs.

### CHANGELOG — **Missing**

No `CHANGELOG.md` exists anywhere in the repository. A ready-to-file draft already exists, though: `Version_1.0_Release_Checklist.md` §3 ("Release notes," lines 82-99+) contains a full `# v1.0.0 — [release date]` body with an "## Included" section referencing the Migration v2 closeout, ADR-0001, and the architecture doc. It has never been extracted into an actual `CHANGELOG.md` file.

### CONTRIBUTING — **Missing**

No `CONTRIBUTING.md`, no contribution guidelines of any kind, anywhere in the repository or in any of the internal engineering documents searched.

### Architecture documentation — **Needs revision**

`Software_Product_Architecture_v1.0.md` is substantial and genuinely complete as content — 25 sections covering product vision, module architecture, pipeline engine, configuration, experiment tracking, plugin system, versioning strategy, and more. The gap is discoverability and placement: it sits at the repository root alongside ~50 other loose `.md` files (migration plans, referee reports, engineering status reports), is not linked from the README (which has no content to link from), and is not under a conventional `docs/` directory. A new contributor has no signposted path to it.

### ADRs — **Needs revision**

Exactly one ADR exists: `ADR-0001_TopicEvolutionRecord_ScopeId_Deferral.md`, a genuinely thorough, well-reasoned document. But there is no ADR system around it — no `docs/adr/` directory, no ADR index or README explaining the convention, no template for future ADRs, and no numbering registry. One good ADR does not constitute an ADR *process* that future contributors can follow.

### LICENSE — **Missing**

No `LICENSE` file exists at the repository root or anywhere else. This is a direct inconsistency with `pyproject.toml`, which declares `license = "MIT"` and includes the corresponding `"License :: OSI Approved :: MIT License"` classifier. A package claiming an MIT license without an actual LICENSE file is a real legal-clarity gap, not just a documentation nicety — anyone consuming the package cannot confirm their actual usage rights from the repository itself.

### Release Notes — **Missing**

Same underlying gap as CHANGELOG: the draft exists in `Version_1.0_Release_Checklist.md` §3 but has never been filed as an actual release artifact, and — per §0 — there is no `v1.0.0` git tag yet to attach release notes to. Only `v0.1.0-phase1` exists.

### Citation instructions — **Missing**

No `CITATION.cff`, no "How to cite this software/study" section anywhere. This is a notable gap given the project's clear academic-publication trajectory (referee-report documents, manuscript figure/table exports, and gold-standard annotation files are all present in the repository), where citation instructions are standard practice and often required by journals for code/data availability compliance.

### Reproducibility documentation — **Needs revision**

The underlying engineering is genuinely strong: `core/reproducibility.py`'s provenance/manifest system (now at 100% test coverage), `enforce_publication_reproducibility()`'s stage-gated checks, `Topic_Evolution_Production_Execution_Guide.md`, and `Production_Validation_Checklist.md` collectively cover most of what a reproducibility statement needs. But it's scattered across five-plus internal engineering documents written for the engineering team, not consolidated into one canonical, user-facing "how to reproduce these results" document.

### Data availability statement — **Missing**

No data availability statement exists anywhere in the repository, despite it containing substantial derived research data (annotation packages, gold-standard samples, sentiment validation sets, manuscript figure data) sourced from YouTube comments. This intersects with both academic-publication requirements and basic data-provenance/ethics disclosure, and is currently undocumented in any form — not even a stub noting what's shareable versus restricted (e.g., `E7_sampling_frame_reference_INTERNAL_ONLY.csv`'s filename implies an access-tier distinction that is never actually documented anywhere).

### Versioning consistency — **Needs revision (critical)**

Three concrete, verifiable inconsistencies:
- `pyproject.toml`: `version = "0.1.0"`.
- `config/settings.yaml`: `study.version: "1.0.0"` (line 48).
- Git tags: only `v0.1.0-phase1` exists; no `v1.0.0` tag has been created, despite `Version_1.0_Release_Checklist.md` §2 specifying the exact `git tag -a v1.0.0` command to run.
- Per §0: the commits that would need to exist under that tag (CI workflow, CLI fix, full R5 test suite) are currently uncommitted.

Additionally, `pyproject.toml`'s `homepage`, `repository`, and `documentation` URLs are all literal placeholders (`https://github.com/REPLACE-ORG/finfluencer-platform`), and the `authors` field is `"Finfluencer Research Group <replace-with-project-email@example.org>"` — also an unfilled placeholder.

### Badges — **Missing**

No badges of any kind (CI status, coverage percentage, license, Python version, PyPI). Consequence, not cause, of the empty README — but also blocked on §0: a CI badge would currently be misleading since the CI workflow itself isn't committed yet.

### Installation instructions — **Missing**

No standalone install guide. `poetry install`-style commands appear only inside internal engineering documents (the CI workflow, the Remediation Plan) — never in user-facing form with prerequisites (Python 3.11-3.15, Poetry), platform notes, or troubleshooting for common install failures.

### Quick Start — **Missing**

Confirmed via full-text search across every `.md` file in the repository: zero matches for "Quick Start" or "Quickstart" in any heading or body text.

### Troubleshooting — **Missing**

Confirmed via the same search: zero matches for "Troubleshoot" anywhere. Some troubleshooting-adjacent content exists informally — `README.txt`'s Windows POSIX-compatibility fix notes are exactly this kind of content — but it's an ad hoc patch note, not part of a maintained troubleshooting document.

### FAQ — **Missing**

Confirmed via the same search: zero matches for "FAQ" or "Frequently Asked" anywhere in the repository.

## 3. Prioritized remediation plan

**P0 — Release-blocking; nothing else should proceed until these close.**

1. **Resolve the uncommitted-work gap (§0).** Commit the CI workflow, the CLI entry-point fix, and the R5/R6 coverage-remediation test suite to `phase2-development` (or merge to `master` first — that branch decision itself needs to be made explicitly, not left implicit). Until this lands, every downstream claim about "R1-R5 complete" describes work that doesn't exist in git history.
2. **Add a real `LICENSE` file** matching the MIT claim already in `pyproject.toml`. This is the single highest legal-risk gap and the cheapest to close.
3. **Reconcile version numbers.** Decide the actual v1.0.0 semantics: bump `pyproject.toml` to `1.0.0` (or explain in writing why package version and study version diverge), fill in the real repository/homepage/documentation URLs and author contact (replacing the `REPLACE-ORG`/`replace-with-project-email` placeholders), then cut the `v1.0.0` tag per the command already drafted in `Version_1.0_Release_Checklist.md` §2 — only after items 1-2 land.

**P1 — Required for a release a stranger could actually use.**

4. **Write a real `README.md`**: project description, install steps, minimal usage example, links to the architecture doc, license, and citation info. Retire or rename `README.txt` so it stops competing for the "README" role.
5. **File `CHANGELOG.md`** from the draft already sitting in `Version_1.0_Release_Checklist.md` §3 — mostly extraction work, not new writing.
6. **Publish Release Notes** as the `v1.0.0` git tag's annotated message and/or a GitHub/GitLab release description, using the same draft.
7. **Write Installation instructions and a Quick Start** — Poetry-based install, Python version constraint (3.11-3.15), first-run walkthrough using `config/settings.yaml`.
8. **Write `CONTRIBUTING.md`** — even a minimal version (branch/PR conventions, test/coverage requirements referencing the now-75.71%-passing suite, code style) is better than none.

**P2 — Research-credibility documentation; matters before any manuscript submission, not just before v1.0.**

9. **Add citation instructions** (`CITATION.cff` plus a README section) given the project's clear academic trajectory.
10. **Write a Data Availability Statement** — what's shareable, what's restricted (the `_INTERNAL_ONLY` file naming convention needs to become an actual documented policy, not an implicit filename signal).
11. **Consolidate reproducibility documentation** into one canonical document, drawing on the already-strong material in `core/reproducibility.py`, the Production Execution Guide, and the Validation Checklist.

**P3 — Structural polish.**

12. **Relocate/link architecture documentation** — either move `Software_Product_Architecture_v1.0.md` (and ADR-0001) under a `docs/` directory or, at minimum, link them prominently from the new README.
13. **Establish an ADR system** — `docs/adr/` directory, index, and template, so ADR-0001 stops being a one-off.
14. **Add badges** to the new README (CI, coverage, license, Python version) — sequenced after item 1, since a CI badge before the workflow is actually committed and running would be inaccurate.

**P4 — Nice-to-have, not release-blocking.**

15. **Troubleshooting guide** — start by formalizing the Windows POSIX-compatibility content currently stranded in `README.txt`.
16. **FAQ** — lowest urgency; can grow organically post-release from real user questions rather than being drafted speculatively now.

No files were modified in producing this audit.
