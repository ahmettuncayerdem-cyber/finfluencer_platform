# Version 1.0 Research Readiness Audit

**Date:** 2026-08-07
**Trigger:** T-029's literal live MVP sign-off (`284912f`, 16/16 checks passed) closed the last
Release blocker. This audit answers a different question than that milestone did: not "does the
pipeline work end-to-end once, live, operated by an engineer," but "can an external researcher
pick this platform up today and run a real, publishable study on it, unassisted." It does not
propose Persistence, Authentication, or any architectural change — those remain correctly
deferred to Sprint 5+. Everything recommended here is documentation, small additive fields, or
file relocation, consistent with "stability over novelty."
**Status:** Planning/assessment artifact — same non-constitutional classification as
`RELEASE_BLOCKING_ASSESSMENT.md`. Does not modify the Roadmap.
**Method:** direct inspection of `master_table.py`, `snapshot_adapter.py`, `pdf_renderer_adapter.py`,
`reporting_engine.py`, `analysis_run.py`, `core/reproducibility.py`, `config/settings.yaml`,
`README.md`, `CONTRIBUTING.md`, `docs/` structure, `pyproject.toml`, `CITATION.cff`,
`CHANGELOG.md`, `.gitignore`, and repo-root `ls`/`git status`. Findings below are quoted from that
inspection, not inferred.

---

## Executive Summary

The engineering core is genuinely solid: T-029's live run just proved the full
Collection→Preprocess→Topics→Sentiment→Report→Export loop works against real YouTube data with
real models, 818+ tests pass, CI is green cross-platform, and this engagement's own governance
discipline (Engineering Gate, root-cause-from-evidence, documented deltas) has held for the
entire build. That is not in question.

What this audit found is a **second, different kind of gap**: the platform is production-tested
from an *engineer's* seat and essentially undocumented from a *researcher's* seat. Nobody outside
this engagement could today discover the API exists, start it, run a study, or correctly interpret
the CSV they'd get back — not because anything is broken, but because no researcher-facing
documentation was ever written (all documentation produced this engagement is internal
engineering/governance paper trail). Separately, the artifacts a paper would actually cite (the
master-table CSV, the PDF) carry no model-version or run-ID field, so today a specific number in a
future manuscript cannot be traced back to the exact model/run that produced it without manually
cross-referencing a separate `provenance.json` file — the architecture document's own AIG-001
requirement for this is an explicit, acknowledged TODO in `analysis_run.py`, not an oversight this
audit is discovering fresh.

None of this is a reason to distrust the numbers the pipeline already produced — it's a reason not
to hand the platform to a researcher yet without a short, scoped stabilization pass first.

## 1. Research Readiness Audit

**Can a researcher run a complete study without touching source code?** Partially, and only if
they already know the internals.

- **Config layer is genuinely good news.** `config/analysts.yaml` and `config/settings.yaml` are
  extensively, self-explanatorily commented — a researcher could plausibly swap in a new
  channel/analyst roster (`handle`/`channel_id`/`pilot`/`expertise_class` fields are all
  documented inline) without reading Python. This is the one place "research usability" already
  exists.
- **Everything else does not.** `README.md` documents only the legacy CLI pipeline
  (`poetry run finfluencer run/analyze/...`) — it never mentions `uvicorn`, `fastapi`, `/docs`
  (Swagger), or the Project→CollectionRun→AnalysisRun→Report→Export workflow that T-029 just
  proved works. The only place the API server's start command appears in the whole repo is a
  buried line in an internal QA checklist (`docs/implementation/SPRINT_0_RELEASE_VERIFICATION_CHECKLIST.md`).
- **No worked example is framed as one.** `t029_live_verification.py`/`t029_e2e_verification.py`
  are the only code that exercises the full researcher-visible workflow end-to-end, but both
  docstrings frame them purely as internal sign-off scripts, and every reference to them elsewhere
  is engineering-verification context — never cited as a usage tutorial.
- **Error handling/robustness from a researcher's chair is untested territory.** This entire
  engagement's testing (unit tests, T-029's own script) exercises the happy path plus a narrow set
  of engineer-anticipated failure modes. What a confused non-developer sees when, e.g., their
  `YT_API_KEY` is wrong, or a channel handle doesn't resolve, has not been evaluated for
  clarity — that requires either a real dry run with a non-developer or a deliberate error-message
  pass.

**Conclusion:** technically capable, operationally inaccessible. This is the readiness dimension
this stabilization pass should prioritize first, since it blocks the stated primary objective
before any publication-quality question even arises.

## 5. Research Workflow Validation

Simulated from the code and documentation as they exist today (not a live dry run with an actual
outside researcher, which this audit could not perform): a researcher who knows nothing about this
codebase's internals would get stuck at step one — discovering the API exists and how to start
it — because `README.md` documents a different (legacy CLI) workflow entirely. If handed the
`t029_live_verification.py` script directly by a developer, they could plausibly copy its request
shapes into their own script or a Swagger UI session and complete the full workflow, since the
underlying pipeline is proven to work (T-029, 16/16). So: **possible with developer hand-holding
today, not possible from documentation alone.** This is the single highest-leverage fix available,
since it requires no code change, only writing down what T-029's script already proves works.

**Operational limitation to flag explicitly, not to build against yet:** there is no Persistence
Layer (correctly out of scope for this freeze, per standing instruction and this engagement's own
Sprint 5 sequencing). This means a real study's collected/analyzed data lives only in a process
temp directory (e.g., `t029_live_verification.py`'s own run wrote to
`C:\Users\...\AppData\Local\Temp\t029-live-...`) until manually copied out. For a real, multi-day
research project, **the research team must adopt a manual procedure** — copy every run's exports
out of the temp location immediately, before the OS or a reboot reclaims it — since the software
itself does not yet guarantee persistence. This is a process/documentation recommendation, not a
proposal to build Persistence now.

## 6. Publication Readiness

The specific, code-verified gaps (not speculation):

- `master_table.py`'s `build_master_table()` output columns: `comment_id, video_id, analyst_key,
  posted_date, text_clean, n_tokens, likes, sentiment_class, sentiment_prob, topic_id_pooled,
  topic_label_pooled, topic_prob_pooled, topic_id_within, topic_label_within`. Raw comment text
  and channel/video identifiers are present — good, this supports qualitative spot-checking and
  re-analysis. But **no `analysis_run_id`, `model_name`, `model_revision`, or `run_timestamp`
  column** — a specific row cannot be traced to the exact model/run that scored it without
  manually cross-referencing `provenance.json`, a separate file.
- `posted_date` is date-only ("already day-truncated by the provider" per `collect/comments.py`) —
  no intra-day granularity. Fine for narrative/topic-sentiment framing questions; a constraint
  worth stating explicitly in any Methods section that touches timing.
- `sentiment_prob` is a single scalar, not a full class-probability distribution — limits any
  calibration/uncertainty analysis a reviewer might ask for.
- Citations (`CitationSnapshot`) carry `record_id, analysis_run_id, kind, selector, content` —
  `analysis_run_id` is present here (unlike the CSV), but not `analysis_type_version` or the
  model name/revision itself. `AnalysisRun` does store `analysis_type_version`, but there is no
  `AnalysisType` catalog wired up anywhere to resolve that string to a concrete model — an
  explicit, already-acknowledged gap in the codebase's own docstrings, not a new finding.
  `PRODUCT_ARCHITECTURE.md`'s AIG-001 requires a manifest hash + model/prompt version on every
  InterpretationRecord; `analysis_run.py` has this as an explicit unimplemented TODO.
- `config/settings.yaml`'s `replication.stage` (four-tier enum gating HuggingFace revision-pin
  strictness) is currently `"exploratory"` — the most permissive tier — despite being past MVP
  sign-off. `provenance.json` (git SHA, config hash, environment versions, seed) is genuinely
  rigorous when it exists, but is a standalone file, not linked by ID to the CSV/Report/citations.
- The PDF renderer's own docstring states its layout is "minimal... publication-quality layout
  deferred" — title + citation headers + a 20-row-capped JSON preview, no title page, authors, or
  methods section. Fine as a working artifact, not as a submission-ready figure/table source.
- No codebook exists anywhere explaining these fields to a research audience.

**None of this means the underlying numbers are wrong.** T-029 proved the pipeline computes real
BERTopic/transformer output over real data. The gap is entirely in *traceability and
documentation* of what produced a given number — which is exactly what a rigorous reviewer would
ask about, and exactly what's fixable without touching architecture (add columns, wire an existing
enforcement setting to a stricter tier, write a codebook).

## 7. Risk Assessment

| Risk | Category | Why |
|---|---|---|
| No researcher-facing documentation exists | **High** | Blocks the stated primary objective outright — a researcher literally cannot self-serve today. Fixable by writing docs; not a code defect. |
| No model/run provenance travels with exported artifacts | **High** | A reviewer asking "which model/revision produced this number" cannot be answered from the CSV/PDF alone today. Fixable with additive columns; not an architecture change. |
| `replication.stage` still at the permissive `"exploratory"` tier | **Medium–High** | A one-line config change, but must be tested — flipping it could newly reject something the pipeline currently tolerates silently (`core/reproducibility.py`'s enforcement is real and could surface a currently-latent gap). |
| **Language/domain match for the Gaza War pilot is unverified** — see §9 | **High, pilot-specific** | The configured sentiment model (`savasy/bert-base-turkish-sentiment-cased`) and one topic-embedding component are Turkish-tuned. If "international news channels" means non-Turkish-language comments, sentiment output would be invalid without a model swap. This needs an explicit answer before the pilot starts, not an assumption either way. |
| Two unexplained live-run crashes from the T-029 sign-off session, correlated with (not proven caused by) low battery, never reproduced under stable power | **Medium** | Non-blocking per T-029's own criterion (already resolved, `BACKLOG.md`), but real research runs will be longer and heavier than a single sign-off pass — worth a `py-spy`-instrumented rerun if it recurs during the pilot. |
| Repo-root clutter (~140 stray tracked+untracked files) | **Medium** | Cosmetic/professionalism risk for a citable public repo, not a functional one. |
| `CITATION.cff`/`pyproject.toml` placeholder URLs, version-number mismatch | **Medium** | Same category — matters for real citability, not functionality. |
| PDF export explicitly non-publication-layout; single-scalar `sentiment_prob` | **Low** | Known, already self-documented limitations; workable for a first pilot's internal review, worth revisiting before final manuscript figures. |

Per the stated instruction, only Critical/High items should block Version 1.0. Nothing here rises
to **Critical** (nothing is broken or produces wrong numbers) — but three items are genuinely
**High**, and this audit's recommendation is a short, scoped pass on those three before treating
the platform as "trustworthy for real academic studies" (the stated primary objective), not a full
Version 1.0 freeze with zero further changes.

## 8. Version 1.0 Freeze Plan

Minimal, stability-only, no new features, no architecture:

1. Repo-root hygiene pass (§4 checklist) — mechanical, low-risk, no code behavior change.
2. Add `analysis_run_id` + model name/revision as columns on the master-table export and fields
   on `CitationSnapshot` — additive, non-breaking (existing consumers ignore new columns), directly
   closes the traceability gap in §6.
3. Flip `replication.stage` to `"submission"` and re-run the full test suite + a fixture-backed
   E2E pass to confirm nothing that currently passes silently starts failing — a verification
   step, not new code.
4. Write the researcher quickstart + output codebook (§4/§1) — pure documentation.
5. Reconcile `CITATION.cff`/`pyproject.toml` placeholders and the version-number mismatch, then
   tag the resulting commit as the real, accurate Version 1.0.

Each step is independently small and reversible — consistent with "backward compatibility
whenever possible" and "never rewrite working components." None of them touches Persistence,
Authentication, or existing architecture. **This audit does not execute any of these five steps —
they are presented for the operator's approval, same discipline this engagement has used for every
prior scope-adjacent decision** (e.g., the PDF-preview design question, put to the operator via
AskUserQuestion rather than decided unilaterally).

## 9. First Real Research Project: Gaza War Strategic-Narrative Study

This pilot serves two purposes at once — a publishable output and a real-world validation of the
platform — and validates fundamentally different things than T-029 did. T-029 proved the pipeline
*executes*. A real study proves the pipeline's *outputs are meaningful* for a genuinely different
research question and content domain than finfluencer sentiment.

**Open question that must be answered before this pilot starts, not assumed:** which language are
the target YouTube comments in? `config/settings.yaml`'s sentiment model
(`savasy/bert-base-turkish-sentiment-cased`) is Turkish-specific; one topic-modeling embedding
component (`paraphrase-multilingual-MiniLM-L12-v2`) is multilingual, but the sentiment classifier
is not. If "international news channels" means English-language content (CNN, BBC, Al Jazeera
English, etc.), sentiment output would not be valid without swapping in a different model first —
a config change, not an architecture change, but one that must happen deliberately, not be
discovered mid-study. If the intended channels are Turkish-language coverage of the Gaza war
(plausible, and would require no model change), this is a non-issue — but this audit cannot assume
either way and flags it explicitly rather than guessing.

**Construct-validity risk, distinct from the technical question above:** this repository already
contains evidence (`E7_annotation_package_n500.csv`, `E7_calibration_pilot_n30.csv`,
`gold_standard_sample_n500_*`, adjudication logs found in §2) that the finfluencer sentiment model
was validated against a human-coded gold sample before being trusted. **The same discipline must
be repeated for this new domain** — a model tuned on financial-influencer sentiment carries no
guarantee of validity on geopolitical-conflict discourse, where "positive"/"negative" framing
operates very differently (grief, outrage, solidarity, propaganda framing vs. financial optimism/
pessimism). Technical pipeline compatibility is not the same claim as construct validity for a new
domain — this pilot's own credibility as an SSCI submission depends on treating that as an open
empirical question, not an assumption.

**Modules exercised beyond T-029's own run:** the same full pipeline, but at plausibly much
larger comment volume and velocity than a financial-influencer channel typically sees (a
war-narrative topic on international news channels likely draws far more comments, faster, with
more moderation/deletion churn and more spam/bot activity) — this stresses the collection and
preprocessing stages differently than anything tested this engagement. It also exercises the
`analysts.yaml`/channel-roster swap path for the first time in real conditions (previously
theoretical, per §1's finding that config is well-documented but never actually exercised with a
different roster).

**Bug classes plausible under this load profile, based on what this engagement has already found
twice:** both prior real-scale defects this engagement discovered (unfilled HuggingFace revision
placeholders; PDF renderer pathologically slow on large unbroken JSON) were invisible at fixture
scale and only surfaced at real data volume. A higher-volume, higher-velocity topic should be
expected to surface a third class of this same pattern somewhere in collection or preprocessing —
budget time for it rather than treating a clean T-029 pass as proof nothing else is scale-sensitive.

**What must be manually verified, not just trusted:**
- A human-coded gold sample of Gaza-war-domain sentiment classifications, with inter-rater
  reliability reported, before trusting any sentiment number in the manuscript — same discipline
  this repo's own `E7_*` files show was already applied once.
- A manual read of a sample of BERTopic's topic labels for coherence/interpretability in this new
  domain — topic quality on political-conflict discourse can differ meaningfully from
  finfluencer discourse even with the same algorithm.
- The PDF/CSV export's completeness on a much larger dataset than any tested this engagement — the
  bounded-preview PDF fix (§6) was validated at 50,000 synthetic rows; confirm real Gaza-war-scale
  volume doesn't exceed that assumption.

**Logs and artifacts to preserve for the eventual paper's reproducibility statement:** the full
structured (structlog JSON) run log, `provenance.json` (git SHA, config hash, environment
versions, seed), the exact `analysts.yaml`/`settings.yaml` used, the master-table CSV and PDF
export, and — critically, given §7's persistence limitation — copies of all of these moved out of
the temp directory immediately after each run, plus a git tag on the exact commit used, so the
paper can cite a precise, immutable software version per `CITATION.cff`.

## 10. Success Criteria for Version 1.0

Measurable, not aspirational:

1. A researcher unfamiliar with this codebase can go from reading the quickstart to a completed
   Report export in a bounded time (e.g., under 2 hours) using documentation alone — no developer
   contact.
2. Every number that reaches a manuscript table is traceable, by a persisted ID in the exported
   artifact itself, to the exact model name + revision + `analysis_run_id` that produced it.
3. `replication.stage` is at `"submission"` or `"publication"` tier for the actual pilot study, not
   `"exploratory"`.
4. The Gaza War pilot completes at least one full Project→Collect→Analyze→Report→Export cycle with
   zero developer code intervention required mid-study.
5. A human-coded gold sample + inter-rater reliability statistic exists for Gaza-war-domain
   sentiment before any sentiment number is treated as reportable.
6. Zero data-integrity surprises are discovered by the researcher rather than caught in QA (e.g.,
   mistaking the PDF's bounded preview for the complete dataset).

## Go / No-Go Recommendation

**Conditional Go.** The engineering core — the part T-029 verified — is genuinely trustworthy:
real data, real models, real end-to-end proof, disciplined governance throughout. Freezing the
*architecture* as Version 1.0, as instructed, is well-supported by the evidence in this audit.

Declaring the platform *"immediately usable for real SSCI-level publications"* without the five
steps in §8 is not supported by the evidence: today, a researcher cannot self-serve the workflow
from documentation, and a number in the exported CSV cannot be traced to the model/run that
produced it without manual cross-referencing. Both are small, additive, non-architectural fixes —
consistent with the stated engineering philosophy — not reasons to reopen scope. This audit
recommends completing §8's five steps (estimated low effort, no architecture touched) and
resolving §9's open language/domain question before starting the Gaza War pilot for real, rather
than discovering either gap mid-study.
